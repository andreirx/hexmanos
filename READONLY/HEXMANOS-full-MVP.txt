We need a **Fixed State Machine** so the game engine knows what to play when.
*   **Schema:**
    *   `IDLE` (Required, Loop, Suggest 2-4 frames)
    *   `WALK` (Required, Loop, Suggest 4-8 frames)
    *   `ACTION_BUILD` (Optional, Loop, e.g., hammering)
    *   `ACTION_ATTACK` (Optional, One-shot)
*   **Frame Policy:** **Flexible Count**.
    *   *Why:* Forcing exactly 4 frames limits creativity. Supporting `min: 1, max: 8` allows for simple or smooth animations. The engine simply cycles `currentFrame % totalFrames`.

### 3. The Map Layering (MVP)
*   **Layering:** **Dual Layer**.
    *   **Layer 0 (Ground):** Grass, Dirt, Water (Must exist).
    *   **Layer 1 (Object):** Trees, Walls, Buildings (Optional, sitting on top).
    *   *Collision Logic:* Defined on the Tile metadata. If Layer 1 exists and is `collidable: true`, the cell is blocked.
    *   *Why:* Single layer is too restrictive (can't put a flower on grass). Dual layer is the minimum viable for a "Base Building" feeling.

This is the **"Pointer Pattern"** architecture.

### Why this is superior
1.  **Immutability:** Once a version of an asset is written to S3, it is a file. It doesn't care about Postgres transaction limits.
2.  **Performance:** The Game Client will load assets directly from S3 (via CloudFront/CDN). The Game Server doesn't need to proxy the data bytes. This saves your M1 Max/AWS Compute bandwidth.
3.  **Resilience:** If the DB dies, you lose the *index* (who owns what), but the *assets* (the actual drawings and logic) are safe in the bucket.

### How "The Editor" writes to this (MVP Flow)

When the user hits **Submit** in the frontend:

1.  **Frontend** generates the JSON locally:
    ```json
    {
      "name": "Knight",
      "animations": { "idle": [0, 1], "walk": [2, 3] },

    ```
2.  **Frontend** asks Backend for a **Presigned S3 Upload URL** (secure direct upload).
3.  **Frontend** uploads `sprite.png` and `meta.json` directly to S3.
4.  **Frontend** calls `POST /api/assets/register`.
5.  **Backend** validates the S3 files exist, then creates the row in `asset_index` with status `PENDING`.

### How "The Game" reads this

1.  **Client** connects to Server.
2.  **Server** sends list of Asset IDs required for this map: `["uuid-grass", "uuid-hero"]`.
3.  **Client** constructs URLs: `https://cdn.yoursite.com/tiles/uuid-grass/tile.png`.
4.  **Client** downloads and caches them locally.

### Submission Workflow

The `status` field on each asset table handles the workflow:

```
draft → pending → approved
                → rejected (can resubmit → pending)
```

- **draft**: Player is still editing. Not visible to admin.
- **pending**: Player submitted. Appears in admin moderation queue.
- **approved**: Visible in game library. Usable in games.
- **rejected**: Player sees rejection note. Can edit and resubmit (returns to pending).

No separate `submissions` table needed — status lives on the asset itself.

### Part 1: Final Architecture Decisions

**1. Spawn Points: Option A (Fixed)**
*   **Decision:** Fixed `(x,y)` coordinates defined in the Map Editor.
*   **Reasoning:** Deterministic behavior is critical for debugging. "Random zones" introduce edge cases (spawning inside a wall or on top of another player). In a turn-based grid game, starting positions are tactical; they should be designed, not random.

**2. Game State Persistence: Option B (In-Memory + Snapshot)**
*   **Decision:** State lives in Java Heap (`GameRoom` object). Scheduled task snapshots to Postgres every 30 seconds + on `RoomClose`.
*   **Reasoning:** Even in turn-based games, writing to disk (DB) on every packet (movement, cursor hover, lock request) creates unnecessary I/O latency. Since we are running on your M1 Max, memory is fast and abundant. The snapshot protects against a server crash losing more than 30s of progress.

**3. Asset Versioning: Option A (Immutable/Versioning)**
*   **Decision:** Editing an asset creates `v2`. Existing games keep `v1`. New games use `v2`.
*   **Reasoning:** "Safety Critical" mindset. If a kid is running a game and the map author deletes a bridge in `v2`, the running game breaks if it auto-updates. Assets must be immutable once approved.

**4. Deletion Policy: Option A (Soft Delete)**
*   **Decision:** `status = 'ARCHIVED'`. Data remains in S3/DB.
*   **Reasoning:** Audit trails. If someone uploads something inappropriate, you need the evidence even after removing it from public view.

**5. Public Metrics: Show Player Count**
*   **Decision:** Show "3/5 Players" or "Active".
*   **Reasoning:** Social proof. Empty servers discourage new joins. Seeing numbers encourages participation.
